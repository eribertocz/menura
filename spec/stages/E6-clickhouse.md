# E6 Generate SQL: ClickHouse

From 1.1.0 the dialect `clickhouse` generates SQL for ClickHouse. It uses the plans E1 to E5 produce, unchanged (P5), and the rules of E6-1 to E6-4 and E6-6, with the changes this chapter states. Only the text of `sql`, the names in `result_schema.physical_type` and the parameter form differ from DuckDB, and every query returns the same rows on both engines. Where ClickHouse's own behavior differs from DuckDB's, the generator writes explicit SQL that gives DuckDB's result; the SQL form is internal (E6-4.14), and execution proves it (E6-7.10). This chapter enters the coverage scope at the 1.1.0 gate (CS-2.6).

## E6-7 Rules

| ID | Rule |
|---|---|
| E6-7.1 | **Identifiers.** Identifiers are quoted with double quotes and keep the catalog's exact spelling and case, as E6-4.3 requires; ClickHouse identifiers are case-sensitive. A relation `source` (E6-4.3) has one part, `table`, or two parts, `database.table`, which name the ClickHouse database and table. A relation `source` of three or more parts cannot be expressed, because ClickHouse names a table with at most two parts: compilation fails with `E6-01` at `dataset:` of the first such dataset in the order E6-4.12 emits its scans, before the check of E6-7.12, and no part is dropped or joined. Internal names the generator introduces (common table expressions, aliases) never equal a column name of any relation the statement reads, so no alias shadows a column. |
| E6-7.2 | **Types.** A logical type (CAT-4.1) is written as: `boolean` → `Bool`; `integer` → `Int<bits>` when signed and `UInt<bits>` when not; `decimal(p,s)` → `Decimal(p, s)`; `float` → `Float32` or `Float64`; `text` → `String`; `binary` → `String`; `uuid` → `UUID`; `date` → `Date32`; `timestamp` with time zone → `DateTime64(<d>, 'UTC')`, `<d>` 0, 3, 6 or 9 for precision `s`, `ms`, `us` or `ns`; `list<T>` → `Array(<T>)`, with `Nullable(<T>)` elements when the elements may be NULL. A nullable scalar is `Nullable(<type>)`. `result_schema.physical_type` holds these names instead of E6-5.6's. |
| E6-7.3 | **Parameters.** In place of the `$n` form of E6-4.2 and the cast of E6-4.2c, the parameter at position n is written `{pn:<type>}` (`{p1:Int64}`), `<type>` the name of E6-7.2 for its logical type, so the type travels with every use. `parameters` keeps its order and encoding (CON-4); an executor binds position n to the query parameter `pn` (over HTTP, `param_pn`), written in ClickHouse's text form for that type, with NULL written `\N`. |
| E6-7.4 | **Null-safe equality.** In place of `IS NOT DISTINCT FROM` (E6-4.7), keys are compared so that two NULL values are equal and a NULL value never equals a non-NULL one, in `JOIN … ON` and in every other clause. |
| E6-7.5 | **Runtime errors.** In place of `error(…)` (E6-4.6b), a runtime condition is raised with `throwIf`, whose message is the constant message E6-4.6b states (E6-4.11). It is evaluated only for the rows where the condition holds, so it never fires on other rows. ClickHouse adds its own prefix to the error, so the executor's error contains the message rather than starting with it (CS-2.4c). |
| E6-7.6 | **Time.** Grains are truncated in the query time zone, with the time-zone argument on every call; ISO weeks start on Monday, never on ClickHouse's default Sunday-based week mode. A `timestamp` value is converted to the query time zone before truncation, and the result is cast back to `Date32` for a `date` field, as E6-5.2 does for DuckDB, so no result falls back to ClickHouse's narrower `Date` range. |
| E6-7.7 | **List membership.** List parameters test membership with standard NULL semantics, as E6-5.3 gives in DuckDB: `x IN list` is true when `x` is an element, NULL when `x` is NULL or when `x` is not an element and the list holds NULL, and false otherwise; `NOT IN` is its negation. ClickHouse's own `IN` ignores NULL elements, so the generator writes the test explicitly. |
| E6-7.8 | **Settings in the statement.** Every statement ends with one `SETTINGS` clause on its outermost `SELECT`, which fixes each server setting its meaning depends on. The clause includes at least `join_use_nulls = 1` (outer joins produce NULL, not default values), `transform_null_in = 0`, `aggregate_functions_null_for_empty = 1` (an aggregate over no rows is NULL, not a default value), `enable_extended_results_for_datetime_functions = 1`, and the settings that fix alias resolution and short-circuit evaluation (E6-7.1, E6-7.5); the generator crate documents the full list with the reason for each. A query whose meaning would depend on a setting missing from that clause is a defect (E6-4.10). The executor's user must be allowed to change these settings per query (ClickHouse `readonly` 0 or 2). |
| E6-7.9 | **Arithmetic.** Division, casts and decimal arithmetic follow E6-4.5, E6-4.6 and E6-4.10 with explicit ClickHouse casts, so a result type never depends on ClickHouse's promotion rules (`/` returning `Float64`, `count` returning `UInt64`, `sum` widening). Integer and decimal arithmetic never wraps: a value that does not fit its result type raises a runtime error, as DuckDB does, instead of ClickHouse's silent overflow. A division by zero gives NULL wherever E6-4.6 says so, never `inf` or `nan`. |
| E6-7.10 | **Verification.** CI executes the generated SQL of every `plan` case on the ClickHouse version pinned by the project, a long-term-support release. The settings of E6-7.8 are set to the opposite value at the session level and the server time zone is not UTC. Before a case runs, the runner builds the case's data in DuckDB as CS-4.2 states and copies every source relation into ClickHouse under the same database and table names, each column with the ClickHouse type E6-7.2 gives its logical type. The rows are compared with the case's expected rows, which are the same for both dialects (CS-2.4). The compatibility matrix records the pinned version (CI-4.3). |
| E6-7.11 | Integrity-check queries (E6-6.2) are generated for ClickHouse by the same rules. |
| E6-7.12 | **Values the dialect cannot express.** When the plan reads, computes or returns a value whose logical type has no ClickHouse type, anywhere (a field, a metric, a returned column, or a value inside an expression such as `CURRENT_TIMESTAMP` or a `TIMESTAMP '…'` literal), compilation fails with `E6-01`; it is never an internal error. Its location is the first query element, in the order E2 checks them (E2-5), whose evaluation needs such a value, as `field:` or `metric:` of that element; when only a row policy or another model expression needs it, the location is `dataset:` of the dataset that holds the expression. The types are `time`, `interval`, `timestamp` without time zone, and a nullable `list` (ClickHouse has no `Nullable(Array(…))`). A `date` or `timestamp` parameter outside the range of its ClickHouse type (`Date32` and `DateTime64` cover 1900-01-01 to 2299-12-31, and only up to 2262-04-11 with precision `ns`) fails the same way. It is checked after E5 and before any SQL is written, so it never depends on the generated text. |
| E6-7.13 | **Catalog mapping.** A catalog producer for ClickHouse maps physical types as the table below states. It reads through `LowCardinality(…)` and `Nullable(…)`, in that nesting order, to the inner type; nullability goes to the column's `nullable` (CAT-4). Every type the table does not list is `unsupported` (CAT-4.3), `Decimal(P, S)` with P above 38 included. A `DateTime` or `DateTime64` without an explicit time-zone argument is `unsupported`, because its meaning depends on the server or session time zone (P1). |
| E6-7.14 | **Floats, text and UUIDs.** Comparisons, grouping and ordering treat a float NaN as DuckDB does: NaN equals NaN and sorts after every other value. Text functions count and change characters, not bytes, as DuckDB does (ClickHouse's `UTF8` variants). `uuid` values compare and sort as their canonical text, not as ClickHouse's internal order. |
| E6-7.15 | **Ordering.** Every `ORDER BY` key writes `NULLS FIRST` or `NULLS LAST` explicitly (E6-4.8). |
| E6-7.16 | **Time-zone database.** E6-5.5 applies: the plan's `producer` declares the time-zone database version the compiler used. ClickHouse uses its own embedded time-zone data, and the compatibility matrix records its version for the pinned release. |

| ClickHouse type | Logical type (CAT-4.1) |
|---|---|
| `Bool` | `boolean` |
| `Int8`, `Int16`, `Int32`, `Int64`, `Int128` | `integer`, `bits` 8, 16, 32, 64, 128, `signed: true` |
| `UInt8`, `UInt16`, `UInt32`, `UInt64`, `UInt128` | `integer`, `bits` 8, 16, 32, 64, 128, `signed: false` |
| `Decimal(P, S)` with P at most 38 | `decimal`, `precision` P, `scale` S |
| `Float32`, `Float64` | `float`, `bits` 32, 64 |
| `String` | `text` |
| `FixedString(N)` | `binary` (zero-padded to N bytes, as ClickHouse stores it) |
| `UUID` | `uuid` |
| `Date`, `Date32` | `date` |
| `DateTime('<zone>')`, `DateTime64(P, '<zone>')` with P 0, 3, 6 or 9 | `timestamp`, `precision` `s` (`DateTime`, or P 0), `ms`, `us` or `ns`, `with_time_zone: true` |
| `Array(T)` | `list`, `element` the mapping of `T` |

`binary` values are written `String` in SQL (E6-7.2) and read back from `FixedString` or `String` columns alike.

## E6-8 Errors

| Code | Condition |
|---|---|
| `E6-01` | The plan reads a relation, or reads or returns a value, that the target dialect cannot express (E6-7.1, E6-7.12). |
